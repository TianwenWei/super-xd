# 下一阶段开发方向：统一任务能力，分离前后台运行方式

- 日期：2026-10-16
- 状态：开发建议，尚未实施；已按后续角色与交付流程讨论修订
- 依据：本轮架构讨论、GPT-6 Astra High 的独立评审，以及对当前仓库实现的只读检查。

本文中的 Task Agent、任务封套和新字段都是建议设计。代码中的 Talker、Vehicle Planner、Thinker 仍按当前规则运行。本次仅调整方案文档，没有修改运行代码、提示词或 AGENTS.md。

## 1. 先说我们准备做什么

下一阶段的核心方向是：**保留 Talker 的快速交互能力，由统一 Task Agent 承担复杂任务，包括车控规划；同一种 Task Agent 可以在当前轮或后台运行。最终架构取消独立 Vehicle Planner agent。**

Task Agent 的业务任务能力应覆盖 Talker 的业务任务能力，并支持更多处理步骤和资源预算。这里的覆盖不包含会话状态管理、音频调度或绕过执行权限；这些属于 SessionActor 等运行程序。

可以用一个比喻理解：

- Talker 是接待用户的管家，简单事情自己办，复杂事情交出完整工单。
- Task Agent 是处理工单的工作人员，按需使用车控、地图、搜索等专业能力，自己完成任务规划，不再把车控交给另一个 Planner 模型。
- 前台和后台是工单的运行方式，不是两种不同职业。
- SessionActor 是执行调度与会话状态的负责人，决定一个动作现在是否可以下发。
- 车辆模拟器执行动作并返回回执，只有回执能证明操作成功。

**下一阶段优先交付一个“小而完整”的统一 Task Agent 闭环：同一个 Task Agent 处理一组车控加一个独立查询，能分别推进、澄清、取消并正确交付结果。**

实施中可以短期保留旧 Planner 作为迁移适配，但阶段 A 的适配状态不是最终架构。首个目标架构版本以阶段 A＋B 为范围，验收时复杂车控不再经过独立 Planner 模型调用。

先证明这个闭环可靠，再扩展到“实时路况＋沿途空闲充电站”。后者还需要新的外部数据能力，不能通过改 agent 名字或提示词获得。

## 2. 当前实现与目标设计有什么区别

| 项目 | 当前实现 | 目标方向 |
| --- | --- | --- |
| Talker | 对话、常驻车控、即时查询、委托 | 保持快路径，负责交接和用户沟通 |
| Vehicle Planner | 当前轮内的专门车控规划器 | 取消独立 agent／模型循环；规划职责并入 Task Agent，校验保留为程序模块 |
| Thinker | 持久化后台查询与研究；车辆动作仅建议 | 研究能力和持久化机制并入共同任务实现，作为后台运行方式，权限仍受约束 |
| 前后台差异 | 与车控／研究职责绑定较深 | 单独表达等待方式、任务存活方式和动作授权 |
| 混合请求 | 支持部分多工具组合，但缺少统一目标进度 | 一张完整工单下有多个子目标、依赖和执行分组 |
| 执行权 | SessionActor 组织下发，模拟器返回回执 | 保持这个边界，worker 不直接修改车辆 |

当前 Planner 并非只知道座椅和空调：它也能加载 navigation 子系统，生成设置目的地、途经点、导航偏好的计划。但当前导航只是模拟状态，不提供真实路线计算。

当前代码也并非只能“整句三选一”：Talker 可以一次输出多个工具调用，车控委托与后台任务登记也可以同组出现。主要缺口是：**这些工作还没有共同的目标账本，以及结果出来后继续推进下一步的完整协议。**

## 3. 本文与 AGENTS.md 的关系

这是规划文档，不是修改现有架构约束的授权。阶段 A 及相关规则尚未由人类维护者更新期间，继续遵守以下当前边界：

1. Talker 固定为现有 23 个工具，不新增通用执行入口，不随对话扩展工具集。
2. 非热车控继续经由现有 Vehicle Planner，不让通用任务循环绕过它直接调用。
3. 当前 Thinker 的车辆动作继续是建议，不因统一协议而自动执行。
4. 被打断轮次的迟到模型结果、回执和音频继续按现有有效性检查处理；不得直接挂回旧轮播报或下发动作。
5. 人设只影响表达；任务侧保持中性，不能参与工具选择、参数和权限决定。
6. POI 导航继续要求先在之前轮次展示候选，由用户在后续轮次选定。

本方案的目标已经明确取消独立 Planner。它与当前“非热车控只能经 Vehicle Planner”的规定存在冲突；实施相关阶段前，需由人类维护者更新架构规则。以下是目标变化及迁移处理方式，不是将取消 Planner 留作未决选项：

| 目标变化 | 涉及的现有边界 | 迁移处理方式 |
| --- | --- | --- |
| 用一个统一委托工具替代现有入口 | AGENTS.md §4 工具边界：固定 23 个工具及名称 | 第一阶段保留原入口；后续单独评审工具契约 |
| Task Agent 直接生成并提交非热车控计划，取消独立 Planner | 非热车控必须经 Vehicle Planner | 阶段 A 暂保留旧入口；阶段 B 在规则更新后复用程序校验并移除 Planner 模型循环 |
| 后台任务产出的动作进入执行流程 | 当前 worker 的 suggested_only 契约及过期结果规则 | 定义新的受控执行提案协议，不能把旧建议直接自动执行 |
| 当前轮任务转后台后继续运行 | 当前轮中断、迟到结果丢弃的规则 | 显式交接为有效任务；旧轮回调仍然无效 |

AGENTS.md 仅由人类维护者编辑。实现者不得通过更名或包装工具绕过这些规则。

## 4. “同一种 agent，两种运行方式”具体是什么意思

### 4.1 共享的是能力和协议

“能力相同”的精确定义是：**两种运行方式可以按任务需要使用同一套能力目录，遵循共同的输入、结果、证据和执行协议。**

它不意味着：

- 每次都给模型加载全部工具。
- 所有任务共用一份历史或可互相修改上下文。
- 两种方式必须使用相同推理预算、相同模型参数。
- 前台曾经允许的动作，在后台任何时候都可以执行。
- 必须立即把 API 进程和 worker 合成同一个进程。

“同一种”首先是协议与实现复用。每个任务仍有独立 ID、上下文、预算、权限范围和运行状态。

### 4.2 Task Agent 与 Talker 的能力关系

目标是：`Task Agent 可用的业务任务能力 ⊇ Talker 可用的业务任务能力`。例如常用车控、天气、地点、网页和车书查询，也应能在 Task Agent 内按需使用，并保留同样的数据来源和执行约束。

| 维度 | Talker | Task Agent |
| --- | --- | --- |
| 优化目标 | 即时响应、少量步骤、低延迟 | 在预算内把委托任务处理到可交付状态 |
| 业务能力 | 常用操作、即时查询、简短回答 | 覆盖这些能力，并支持多步规划、查询、比较和条件更新 |
| 交互职责 | 接住用户、选择快路径或委托、理解后续输入 | 完成指定任务，返回结构化结果与中性口语结论 |
| 实际执行 | 通过统一运行程序执行 | 同样通过统一运行程序执行 |

Task Agent 可以使用更多推理资源，但不要求一定使用另一种模型，也不保证每次都更慢。简单任务仍走 Talker，是为了减少交接与任务管理开销。无需为了证明能力覆盖，让所有简单请求绕行 Task Agent。

覆盖的是业务能力，不要求 Task Agent 复制 Talker 的委托入口、人设配置和面向整个会话的任务管理职责。前后台 Task Agent 也不因运行模式不同而获得不同的业务能力上限。

### 4.3 三个维度要分开

| 维度 | 要回答的问题 | 建议示例 |
| --- | --- | --- |
| 交付方式 | 当前轮是否等待结果？ | `current_turn` / `background` |
| 任务存活 | 新话题、打断、断线后怎么办？ | `turn_bound` / `task_bound` |
| 动作授权 | 现在还允许执行哪些动作？ | 只查询、允许明确车控、等待 POI 选择、等待不可逆动作确认 |

前台处理不等于阻塞事件循环。当前轮可以等待，但用户仍能插话或取消。

后台处理不等于无限运行。当前 Thinker 从登记起最多一分钟，排队计入、等待澄清暂停；模式切换和补充条件不能重置预算。第一阶段保留这个规则。

### 4.4 交互示例

| 用户行为 | 系统应如何理解 | 注意事项 |
| --- | --- | --- |
| “别念了，继续查。” | 停止播报，任务继续 | 停止音频与取消任务是两个事件 |
| “酒店那个不用查了。” | 取消指定酒店任务 | 目标由模型指认，代码只操作结构化 task_id |
| “继续查，顺便把音量调低。” | 保持原任务，并处理新车控 | 不因新一轮对话误取消后台任务 |
| “等一下。”且上下文不明确 | 确定停止对象，必要时问一个问题 | 不能用关键词把所有任务都取消 |

上述是目标语义，不代表当前实现全部支持。第一阶段保持现有中断行为；新的任务存活策略要通过独立评测后再启用。

## 5. 推荐的职责分配

```text
用户
  ↓
Talker：交流、快速处理、交出完整请求
  ├─ 快路径 → 现有工具执行／即时查询
  └─ 复杂任务 → 共同任务协议
                  ↓
              Task Agent：理解目标、条件、依赖，调用专业能力
                  ├─ 自己生成车控结构化计划，调用普通程序校验
                  ├─ 按需使用常用车控、天气、地点、网页和车书工具
                  └─ 按需使用后续新增的路线、沿途搜索和充电状态工具
                  ↓
              任务运行层：持久化状态、推进就绪步骤、校验 revision
                  ↓ 只发送结果或受控提案
              SessionActor：复核当前授权、车况和回执，组织执行
                  ↓
              VehicleSimulator：执行并返回真实模拟回执
```

这是目标架构图，不包含迁移阶段的旧入口。模型角色只有 Talker 和 Task Agent；SessionActor、任务运行层和车控校验器是程序，VehicleSimulator 是模拟执行端。

### Talker：保持轻量

Talker 必须理解用户，但不必在交接前把复杂任务完整规划一遍。它负责决定是否使用快路径，以及交接完整原话和上下文。任务 agent 负责复杂依赖的理解。

这避免每个复杂请求都经过“Talker 完整规划一次 → 总 Planner 再规划一次 → 专业 agent 再规划一次”。

阶段 A 可以保留现有两个委托入口，用代码把它们包装为共同任务记录。阶段 B 切到统一 Task Agent 后，复杂车控不再经过独立 Planner 模型。委托工具的最终名称和参数需同步更新仓库契约；不新增一个每轮必经的模型分类器，也不同时让多个模型各自解释并执行同一组车控。

### Task Agent：负责语义和专业调用

它识别目标、条件、先后关系、保持约束和缺失信息，产出结构化安排。它也可以在得到新证据后继续决策。

车控计划由 Task Agent 自己生成，包括 `intents`、`actions`、`depends_on` 和 `keep_paths`；程序负责 schema、来源引用、依赖及保持约束校验和车况副本预演。校验错误返回当前 Task Agent 循环处理，不另请 Planner 模型重做一次。纠正占用任务已有调用预算，不增加独立的“失败后重问”模型阶段。

任务运行层根据结构化状态推进：哪些依赖已完成、哪些节点等待用户、哪些动作不可下发。代码不能用用户文本匹配来补做意图识别。

### SessionActor：保持单一执行入口

worker、模型回调和网络回调均不能直接修改 `self.vehicle`、`self.turns` 或 `self.current`。它们发送事件，actor 在事件处理路径中校验并更新会话状态。

新增 SQLite 同步调用继续放入 `asyncio.to_thread`。任务状态和事件在同一个短事务内提交，不跨网络调用持有数据库事务。

SessionActor 是普通 Python 事件处理程序，不是第三个模型，也不只是一个 hook。它持有会话状态，通过队列接收用户输入、模型结果、任务事件、车辆回执和音频事件，统一决定这些结果现在是否还能采用。

### Task Agent 完成后：回到前台程序，默认不再调用 Talker 模型

默认交付流程：

```text
Talker 模型生成接话内容＋委托调用
  → Task Agent 查询／规划／等待实际执行回执
  → Task Agent 在自己的交付中生成结构化结果＋summary＋spoken_summary
  → SessionActor 检查任务版本、轮次和结果有效性
  → 前台按现有表达路径展示结果、安排 TTS 播报
```

前台模式将结果交回当前有效轮次，后台模式通过任务事件在适当时机交付。两者都不能直接绕过前台程序控制扬声器或车辆。

Task Agent 要生成后续可播报内容，但内容保持中性，保留失败、未核实及尚未执行的限制。前台可做模板表达和朗读格式处理；默认不再调用一次 Talker 模型进行复述或人设润色。

只有结果引出了新的语义决策，例如与用户最新目标发生冲突、需要理解新的选择，才按需进入 Talker 模型。已过期结果先被程序拒绝，不能为了“重新解释”就复活旧动作。

例子：“比较三个餐厅，推荐停车方便的一家。”Task Agent 可同时交付推荐对象、来源和“更推荐第二家，停车信息较明确；儿童座椅是否要预约还没核实”的口语结论。前台校验后直接播报，不必把报告再交给 Talker 模型改写。这里是表达示例，不代表已执行真实查询。

## 6. 完整例子：舒适座舱＋去公司途中充电

用户说：

> 帮我把座椅调到让我舒适的角度，然后打开座椅按摩和香薰；导航到公司，看看哪条路不堵，中途找个空闲充电桩充电。

### 6.1 先保留全部要求，再分组

| 分组 | 子需求 | 必要条件 | 与其他组的关系 |
| --- | --- | --- | --- |
| 舒适设置 | 座椅角度、按摩、香薰 | 用户偏好或明确角度；当前音区和车况 | 本例“然后”是否表示真实依赖由模型判断并记录 |
| 出行规划 | 公司地址、候选路线、沿途充电站 | 起终点、路线工具、充电数据 | 通常不依赖座椅设置完成 |
| 导航执行 | 将选定充电站设为途经点，公司为终点 | 已展示并选定的 POI；有效执行权限 | 依赖出行结果和用户选择 |

不能把“舒服”随意翻译成某个角度；不能把“公司”随意翻译成一个地址；“找到充电站”也不等于“已确认空闲”。

若是主驾，现有模拟规则还要求停车后才能调整座椅位置。执行前必须检查实际车况。

### 6.2 没有保存舒适偏好时

先问一个必要的问题，例如：

> 座椅靠背想往前一点，还是往后一点？

若模型把舒适设置判定为一个有顺序关系的组，按摩和香薰也先等待。不能为了展示“并行”而擅自打散它。

与此同时，公司地址若已通过允许的数据来源明确、且出行工具已接通，则可以推进独立的出行查询。另一个目标缺失信息，不必让所有工作停止。

如果舒适偏好和公司地址都缺失，按影响范围选择一个最关键问题先问，并在任务记录里保留另一个缺口，避免用户回答后丢失剩余要求。舒适偏好和“公司”地址解析是待建设的用户设置能力，当前不能假定存在。

### 6.3 信息和出行工具齐全时

1. Task Agent 自己生成车控组计划，交程序校验；SessionActor 逐项下发并返回回执，不再调用独立 Planner 模型。
2. 出行组查询候选路线及路况，沿候选路线查充电站，再取得接口、功率、空闲状态和查询时间。
3. 以总行程成本比较方案：开车时间、绕路时间，以及有数据支持的等待／充电时间。
4. 如果缺少等待或充电时长数据，单独标记未知，不编造总耗时。
5. 前台告诉用户候选，例如“这条路线旁有两个站，A 站查询时有空闲枪位，B 站暂时无法确认”。这只是未来工具已真实返回相应数据时的表达示例。
6. 用户后续选择站点后，生成途经点与终点操作，复核并执行。

空闲状态只能说明查询时的情况，不代表到达时仍然有空位。不会为了“保证空闲”自动预约、支付或下单；这些属于另一类需内容绑定确认的动作。

### 6.4 当前系统应怎样诚实交付

在路线与充电接口尚未接入时，可以完成明确、有效的模拟车控，必要时搜索真实地点；对路线避堵、沿途性和实时空闲状态明确返回能力缺失。

不得把设置 `prefer_fastest=true` 称为“已经找到最快路线”，不得把一个充电站的网页介绍称为“现在有空位”，也不得把模拟途经点写入称为真实路线已经规划。

## 7. 共同任务协议：至少记录什么

建议增加“任务封套”，可以理解成装着原话、子目标和进度的工单。先作为现有流程外层的共同记录，再决定是否迁移数据库结构。

### 7.1 输入

| 字段 | 含义 | 为什么需要 |
| --- | --- | --- |
| `request_id`、`session_id`、`origin_turn_id` | 整体请求与来源 | 将对话、计划、查询和回执连起来 |
| `original_input`、`input_event_refs` | 原话及后续补充事件 | 摘要不能替代授权依据 |
| `revision` | 用户补充／修改后的语义版本 | 旧条件结果不得覆盖新条件 |
| `delivery_mode`、`lifetime` | 等待方式和任务存活策略 | 避免把前后台与取消绑定 |
| `context_refs` | 车况、音区、地点设置、历史、候选结果引用 | 保留数据来源和取得时间 |
| `capability_ids` | 当前任务需要的能力 | 按需加载，避免全量工具膨胀 |
| `budget` | deadline、已消耗调用和工具预算 | 切换模式不刷新预算 |
| `authorization_refs` | 支持动作的用户事件及范围 | 防止摘要、网页或建议扩权 |

### 7.2 子目标与执行分组

子目标记录：`id`、原话片段、专业能力、状态、依赖、缺失信息、采用的证据和结果引用。

车控执行组记录：动作清单、`depends_on`、`keep_paths`、允许的部分执行范围和已完成操作回执。不能把整个混合请求视为一个需要全成全败的事务；也不能把一个有约束关系的车控组拆散执行。

下面是字段关系示意，不是已经上线的 API，也不是完整模型 schema：

```json
{
  "request_id": "request-example",
  "revision": 1,
  "original_input": "先把主驾靠背调到105度，再开按摩和香薰，同时核实我指定网站上的消息。",
  "delivery_mode": "current_turn",
  "lifetime": "turn_bound",
  "goals": [
    {
      "id": "comfort",
      "capability_ids": ["vehicle.seats", "vehicle.climate"],
      "execution_group_id": "comfort-group",
      "status": "ready",
      "depends_on": []
    },
    {
      "id": "source-check",
      "capability_ids": ["research.web"],
      "status": "waiting_input",
      "missing_fields": ["source_url", "claim_to_verify"],
      "depends_on": []
    }
  ]
}
```

`ready` 表示语义必要字段齐全，不表示车控已经获准执行；仍需检查车况、权限和真实回执。示例中靠背位置对应 `axis=backrest, position=105`。按摩／香薰的默认档位由模型依据功能契约选择，不能由字符串匹配生成。

任务封套保留完整原话。每个子目标还应有原话片段或用户事件引用；为了简洁，上例未展开来源绑定。

### 7.3 输出

统一结果至少区分四类：

| 输出 | 能证明什么 | 不能直接代表什么 |
| --- | --- | --- |
| `evidence` | 工具实际取得的材料、时间、来源 | 资料全部正确、仍然新鲜 |
| `proposal` | 模型提出了一个可校验方案 | 用户已选择、动作已执行 |
| `execution_receipts` | 车端实际成功／失败记录 | 尚未下发的后续动作也成功 |
| `unresolved_items` | 缺条件、缺能力、失败或无法核实的部分 | 可以偷偷忽略这些要求 |

Task Agent 在自己的最终交付中生成中性的 `summary` 和 `spoken_summary`，由前台按现有表达路径交付，不为了复述或人设增加一次 Talker 模型调用。最终交付可能需要任务自身的一次模型调用，它属于 Task Agent 的工作预算，不能把它隐去或声称零成本。

只完成计划时，结果必须写明尚未执行；需要执行的任务只有拿到真实回执后，才可以采用动作完成状态。不能先生成“已经调好”的最终话术，再等待执行结果。

### 7.4 分派子目标时，怎样保留完整原话又不让各模块重复处理

这需要显式协议。目标架构由同一个 Task Agent 管理完整混合请求，不再默认把车控和研究分别交给两个专业 agent。若因独立交付需要创建多个 Task Agent 实例，或者处于旧流程迁移期，也必须明确各自的负责范围；不能让两边都处理全部要求。

建议同时传递两层信息：

- `original_input` 和补充事件：保留完整授权上下文。
- `assigned_goal_ids` 和 `source_refs`：明确本次只负责哪几个子目标，以及它们对应哪些原话片段和跨组约束。

例如主 Task Agent 处理完整“座舱设置＋出行查询”，舒适设置执行组只包含座椅、按摩和香薰。查询节点只产生证据和候选，不直接扩大该车控组的动作范围。每组仍须保留与它有关的跨组条件。

Task Agent 负责理解、分组和规划，专业能力主要通过工具及程序校验提供，不默认叠加专业模型。服务端只检查 ID、精确来源绑定、依赖、已知授权字段和 schema，不通过文本关键词筛选车控句子。精确引用和 schema 合法也不能证明语义理解必然正确，仍须依靠独立评测检验。

现有 Planner 只接收整句 `request_text`，没有这个分派范围字段。阶段 A 若需适配旧流程，必须显式保留负责范围；阶段 B 则由 Task Agent 直接生成分组计划。两种情况下都需更新必要的结构化字段契约和通用 prompt 规则，验证组外要求不会丢失或误执行。不能靠悄悄截短原话来假装已经支持混合编排。

## 8. 状态、取消和迟到结果

### 8.1 区分任务状态与当前轮状态

建议的子目标状态包括：

`pending → ready → running → completed`

另有 `waiting_input`、`waiting_selection`、`failed`、`cancelled`、`blocked`。这些是建议的新封套状态，不是要求直接修改当前 tasks 表的枚举。

整体请求可以记录各子目标完成比例和未完成原因。一个组完成、另一个组失败时显示部分完成，不能把总状态写成“全部成功”。已完成动作不自动回滚，也不在回复后再次执行。

### 8.2 三类停止操作

1. 停止播报：关闭本次音频，不默认改变任务。
2. 停止／取消一个任务：取消指定任务及未下发步骤，保留已执行回执。
3. 修改目标：增加 revision，重新判断材料和动作是否适用，不重置已消耗预算。

用户原话到操作种类、目标 task_id 的映射必须由模型输出结构化字段。代码不能用“停”“算了”等文本片段实现任务路由。

### 8.3 当前轮转后台

长期可以支持，但第一阶段不自动启用。设计时必须做到：

- 转移同一个任务的上下文、已采用证据、完成动作和剩余预算，不重新从零查。
- 写入显式交接事件，确定新的结果接收方；旧轮回调继续作废。
- 交付方式变化不等于用户修改目标，不冒用用户 reply/update 的 revision 语义；可另记运行代次。
- 原本绑定当前轮的动作权限不因模式转换自动延长。
- 超过前台等待阈值只可触发交接策略，不能自动获得后台车控权限。

## 9. 后台结果到执行：必须有受控关口

未来后台任务若需要推动执行，应发出结构化提案事件，而非直接执行车控。关口依次核对：

1. 任务 ID、revision、运行代次仍有效，未取消、未超时。
2. 提案动作有用户原话／补充事件支撑，未扩大对象、数值或动作范围。
3. 依赖步骤有真实完成记录；需要 POI 选择的已选择，需要不可逆确认的已完成内容哈希绑定确认。
4. 最新相关车况与权限适用；执行不能覆盖用户后来直接设置的新目标。
5. 通过从现有 Planner 提取的车控程序校验，再进入 actor 下发流程；目标架构不调用 Planner 模型。
6. 下发使用稳定幂等键，成功／失败依据车端回执。

例子：后台还在查公司充电路线，用户已说“先导航回家”。即使后台公司的方案查询成功，也只能保留为资料，不能覆盖回家导航。

任务 revision 不一定会因另一个直接导航动作改变，所以还应维护相关资源的变更记录，例如导航目标的设置版本，以及该提案依赖的版本。只比较相关状态，避免一次音量变化让所有出行证据失效。版本或条件不一致时停止自动下发，将冲突交回模型／用户处理。

版本比对是代码对结构化字段的校验，不是代码重新理解自然语言。幂等键防止重复提交，不能证明当前仍有权执行。

worker 暂时找不到有效会话执行入口时，不得自行操作模拟器。第一阶段按现有会话生命周期处理；跨重启恢复执行、跨设备继续任务不在首批范围内。

## 10. 出行能力：后续需要补哪些工具

以下名称仅为能力说明，具体供应商和 API 尚未选型；不宣称现有 Google 客户端已提供这些接口。

| 能力 | 最少输入 | 最少输出 |
| --- | --- | --- |
| 地址／别名解析 | 用户认可的“公司”等设置或对话引用 | 明确地址／地点 ID、来源引用；歧义时澄清 |
| 路线查询 | 起终点、出发时间、车辆适用条件 | 路线 ID、路径几何、距离、预计时间、路况依据、查询时间 |
| 沿途搜索 | 候选路线、绕路限制、站点类型 | 站点 ID、相对路线位置、绕路距离／时间、数据来源 |
| 充电状态 | 站点 ID、接口和车辆条件 | 接口、功率、可用枪位、更新时间、未知字段 |
| 行程比较 | 实际候选路线和站点证据 | 采用的方案、比较依据、未核实项 |

当前没有设备 GPS 能力。当前位置设置中的城市／地标不能伪装成实时坐标；真实路线起点必须来自用户认可的明确位置，或后续正式接入的定位能力。

先做供应商能力验证，再接模型工具。验证真实覆盖、数据新鲜度、超时和错误形式。缺凭证直接报错，不回退到虚构路线或虚构空闲状态。

所有正式车控仍为模拟。离线工程测试可以显式注入假数据，但界面、日志和评测必须明确标识测试数据，不能当作真实外部 API 验收。

## 11. 分阶段实施计划

### 阶段 A：统一记录协议，提取车控校验，建立迁移适配

目标：先把现有流程放进同一张可追踪工单，并为移除独立 Planner 准备可复用校验程序。这个阶段允许暂时保留旧调用链，但不能将其当成最终交付架构。

工作：

1. 新增任务封套与结果类型，定义原话、来源、子目标、状态和关联 ID。
2. 给 `delegate_vehicle_control`、`delegate_task` 增加内部适配层；不新增 Talker 工具，不改变现有参数和权限。
3. 建立同一请求到车控计划、后台任务、回执的关联记录。最初可将两个已有委托视为两个子目标，不要求额外模型先做完整拆分。
4. 增加聚合进度展示，完整保留每个子目标的失败、澄清和未核实部分。
5. 从 `vehicle_planner.py` 分离 schema、来源绑定、依赖、保持约束和预演等程序逻辑，原调用链继续使用同一套校验，避免复制后两套规则分叉。
6. 保持现有模型路径、预算与工具执行行为；先验证记录和校验提取没有引入额外模型调用。

交付：类型与字段说明、迁移适配器、共用车控校验模块、必要持久化迁移、trace 字段、第一组回归。

完成条件：同一请求的车控和查询过程能串起来；字段与事件一致；原有快路径通过率和调用次数保持。

### 阶段 B：启用统一 Task Agent，取消独立 Planner，跑通混合请求

目标：同一种 Task Agent 直接承担复杂车控和查询，独立目标能分别推进，依赖组保持完整，查询失败不掩盖已完成车控。

前提：人类维护者先更新非热车控入口与相关工具契约的架构约束。更新前只能完成阶段 A 的兼容工作，不以本方案代替规则变更。

选用现有能力，例如：“主驾加热一档、香薰一档，同时核实某个指定来源的信息”。评测句和 prompt 示例使用不同表达，避免测到背题。

工作：

1. 建立统一 Task Agent 循环，由它在自己的模型调用中理解子目标、分组和引用；Talker 不预先完整规划一次。
2. 为 Task Agent 提供 Talker 已有业务能力的可复用适配，以及结构化车控计划提交协议；车控执行仍通过 SessionActor。
3. Task Agent 直接生成车控计划并使用阶段 A 提取的程序校验，移除复杂车控路径中的独立 Planner 模型循环，不保留隐式二次规划。
4. 同一个任务中处理查询与车控步骤的就绪、等待、执行和结果，允许独立工具 IO 并行，不要求同时启动两个任务模型。创建任务时可选择当前轮或后台交付，两种方式使用同一任务实现；运行中切换和更细的存活策略在阶段 C 完善。
5. 用户补充明确对应已有任务时，更新原任务，不重复登记；同一车控组只由一个入口执行。
6. 交付结构化结果和中性 `spoken_summary`，由 SessionActor 校验后交付；不强制再次调用 Talker 模型。
7. 为中途取消、重复事件、旧 revision、音频抢占和已完成动作加入有意义的工程回归；接入后台车辆提案前，先实现第 9 节关口。
8. 展示真实进度，并安排澄清播报：同一时间最多问一个必要问题，已排队问题在播出前重新检查是否仍有效。

完成条件：复杂车控由 Task Agent 直接规划，独立 Planner 模型调用次数为零；一个目标等待补充时，独立目标仍能完成；已完成动作不重复；没有未授权车控；完整结果可直接通过 SessionActor 播报。

### 阶段 C：完善前后台运行方式和显式交接

前提：人类维护者明确长期工具边界及交接规则。未确定前不实施突破当前约束的部分。

工作：

1. 将旧 Thinker 的预算、checkpoint、来源和事件机制复用于统一任务运行层，取消仅研究任务才能使用这些机制的限制。
2. 同一种任务实现按能力目录加载工具，在当前轮或后台运行；每个任务上下文隔离，业务能力上限相同。
3. 验证当前轮转后台时预算、证据、权限与幂等记录的继承。
4. 分别处理停止播报、取消任务、修改目标；继续保留旧轮有效性检查。
5. 验证两种方式均返回 SessionActor，默认不增加 Talker 润色调用；移除仅为兼容旧入口保留的适配和命名。
6. 完善后台执行提案的相关状态版本与会话重连处理；第 9 节关口仍是开放车辆写操作的必要条件。

完成条件：相同任务两种模式下采用同样的条件、证据和执行约束；模式切换只影响交付和运行生命周期，不改变用户授权。

### 阶段 D：接入真实出行数据，完成用户的完整例子

工作：接入并验证路线、路况、沿途搜索、充电状态及地址来源；让任务使用实际证据比较方案；POI 选定后进入模拟导航执行。

完成条件：能证明“沿途”和“空闲”的数据来源及时间；无法取得数据时诚实部分交付；用户选定后正确设置途经点和终点，旧方案不覆盖后续导航。

阶段顺序代表依赖关系，不是工期承诺。出行供应商调研可提前开展，但不能把接口接通当作任务协作已经完成。

前端面向用户展示“座舱设置”“资料查询”“等待你选择”，工具名、模型调用序号和底层 schema 留在诊断视图。

## 13. 验收：用什么证明方案有效

### 13.1 必测场景

| 场景 | 结构化预期 |
| --- | --- |
| 简单音量指令 | 保持原快路径，不创建任务、不调用新模型 |
| 多个常驻车控，无真实依赖 | 同组直接调用；不强制进入复杂任务 |
| 香薰＋座椅＋独立查询 | 同一个 Task Agent 分组处理；车控经程序校验；关联到同一请求 |
| Task Agent 接到 Talker 能处理的业务任务 | 能使用对应能力，参数、来源和执行约束一致；不代表默认绕行快路径 |
| 复杂车控的目标调用链 | Task Agent 直接生成计划，独立 Planner 模型调用次数为零 |
| 已完成任务的正常交付 | 包含结构化结果及 spoken_summary，前台直接交付；没有强制 Talker 润色调用 |
| 一个目标缺信息 | 该组等待；独立组可继续；缺失条件有字段记录 |
| “先 A，成功后才 B” | B 依赖 A 的真实成功回执；A 失败时 B 不下发 |
| 保持副驾温度，调整主驾温度且存在联动 | 不违反 keep 约束，必要时澄清；不偷偷扩大范围 |
| 取消指定研究任务 | 正确 task_id；旧结果不采用，不取消无关任务 |
| 修改研究条件 | revision 增加；旧材料不自动成为新结论；预算不重置 |
| 任务返回前用户已更改导航 | 旧提案不覆盖最新目的地 |
| POI 本轮刚查到 | 不直接导航；候选先展示，后续用户选择 |
| 重复任务事件或命令重试 | 动作不重复；幂等绑定稳定；完成状态不复活 |
| 当前轮转后台（阶段 C） | 不重复搜索或执行，不续用过期轮次授权，不刷新预算 |
| 路线／充电服务缺失或凭证缺失 | 有明确失败码／未完成项；不生成假路线或空位 |
| 更换人设或文字／语音入口 | 工具序列、参数、任务依赖和权限结果一致 |

### 13.2 评测与测试分工

先把失败场景写入评测，再改模型行为。语义行为用真实模型评测，至少重复三次；运行时竞争、取消、迁移和幂等使用显式依赖注入的工程测试。

现有 `evals.harness` 主要驱动 Talker／Planner 并检查任务登记，不能单独证明后台研究到后续执行的闭环。需要扩展测试驱动，实际推进 worker 和 actor 事件，再比对结构化目标状态、revision、命令和回执。

不通过回复文本判断行为通过率。话术单独做 `speech_review` 抽查，并人工核对至少一条相关完整 trace。

实现阶段的现有检查入口：

```bash
.venv/bin/python -m scripts.validate_prompt_config
.venv/bin/python -m pytest -q
.venv/bin/python -m evals.harness --repeat 3 --out data/evals/task-agent-before.json
.venv/bin/python -m evals.harness --repeat 3 --out data/evals/task-agent-after.json
.venv/bin/python -m evals.speech_review data/evals/task-agent-after.json
```

before 报告必须在行为改动前产生，after 在改动后产生；不能在同一代码版本连续运行两次就当作前后对比。前端有改动时再运行前端测试和构建。prompt 配置变更后按仓库要求重启 API 和 Worker。

### 13.3 延迟与调用次数

现有文档的历史参考值是 2026-10-15 首句可播 P50 约 2.1 秒、平均每轮 1.04 次调用；它不是本轮新测量，也不是所有路线任务的目标。

实施前应重测同一组用例，并按简单指令、即时查询、复合车控、后台研究、混合任务分别报告：

- 首句可播 P50/P90；另外记录首 PCM，不能混为一个指标。
- 首个有效车控回执、各子目标完成及整体交付时间。
- 按模型角色统计调用次数：改动前是 Talker、Planner、Thinker，目标架构是 Talker、Task Agent。另按 API／worker 运行位置统计，避免把耗时转移到 worker 后误称减少调用。
- 复杂车控的独立 Planner 调用次数，以及任务完成后因复述而增加的 Talker 调用次数；目标路径两者均为零。
- 排队与工具耗时，以及供应商实际返回的缓存 token 信息。

建议的阶段验收门槛：简单快路径不增加必经模型调用；同组样本 P50/P90 若相对实施前恶化超过 10%，必须定位并解释原因，再决定是否接受。这是建议门槛，不是已验证的性能结论。

完整评测无新增失败，或对新增失败逐项说明原因与处理决定；不能只展示新例子成功而隐藏旧回归。

## 14. 第一批开发任务与完成后的样子

首个目标架构版本按阶段 A＋B 推进，先完成不改变规则的迁移准备，再在架构规则更新后切换。建议按顺序完成下面五件事：

1. **补充混合任务评测与改动前基线。** 覆盖车控＋查询、独立澄清、真实依赖、取消与旧结果；先扩展必要的结构化观测能力。
2. **定义共同任务封套。** 明确原话引用、子目标、关联 ID、revision、结果和预算，不改变现有工具边界。
3. **提取共用校验并切换统一 Task Agent。** 先适配现有入口，规则更新后由 Task Agent 直接规划车控，移除独立 Planner 模型调用；执行权限仍统一管理。
4. **完成一个真实能力范围内的混合请求。** Task Agent 处理车控与查询，拿真实模拟回执与真实来源；独立目标分别推进，返回前台的 spoken_summary 可直接播报。
5. **补齐任务展示、回归和报告。** 能从界面看到“做完什么、正在做什么、还缺什么”，并用 trace 核对工具、结果和播报一致。

完成这一版本后，用户能提出一个含车控和查询的请求，由统一 Task Agent 保留所有要求、正确安排已有能力并明确呈现进度；缺信息或部分失败时，其他独立工作不会被遗忘。最终调用链没有独立 Vehicle Planner agent，任务交付也不强制回到 Talker 模型复述。

这一版本不承诺完成真实沿途充电导航、不把旧后台建议自动当作执行授权、不放宽 POI 选择要求。它会新增统一 Task Agent 循环并取消独立 Planner；更完整的模式交接与真实出行能力分别在阶段 C、D 完善。

### 术语对照

| 术语 | 本文含义 |
| --- | --- |
| sub-agent | 被委托处理子任务的模型工作单元，不必是独立进程 |
| handoff／交接 | 传递完整任务及上下文；Talker 仍然负责用户交流 |
| Task Agent | 目标架构中覆盖 Talker 业务能力的统一任务处理模型角色；负责复杂规划及可播报结果，不是当前新增完成的类 |
| Vehicle Planner | 当前代码中的独立车控规划 agent；目标架构取消，计划生成并入 Task Agent |
| 车控校验器 | 普通程序，检查结构化计划、来源、依赖、保持约束和车况；不调用模型 |
| SessionActor | 持有会话状态、处理事件、组织执行和播报的普通 Python 程序；不是模型或单个 hook |
| capability／能力 | 车控规划、搜索读取、路线查询等可按需加载的专业工具与规则 |
| 当前轮运行 | 当前对话轮次等待结果；不阻塞事件循环，允许用户插话 |
| 后台运行 | 任务独立登记并跨轮推进；受预算、取消与权限约束 |
| revision | 用户修改／补充后的任务版本，用于拒绝旧条件结果 |
| checkpoint | 已采用材料、消息、预算和进度的保存点，不代表外部请求必定可恢复 |
| proposal／提案 | 待校验或待选择的方案，不等于已经执行 |
| receipt／回执 | 车端实际执行结果，是判断车控成功／失败的依据 |
